# 中文摘要（Traditional Chinese Executive Summary）

## 研究題目

**超越 TOTP：同步通行金鑰與硬體安全金鑰的釣魚抵抗與帳號復原評估**

本研究的核心問題不是「哪一種登入方式最快」，而是「當帳號面臨即時釣魚、
重放攻擊、裝置遺失與復原流程濫用時，哪一種設計仍然站得住腳」。因此，除了
協定分析之外，我也建立了一個可重現的測試平台，實際執行登入、釣魚代理、
重放、裝置遺失、備份與復原流程。

## 方法

我實作 **AuthLab**，一個以 Flask 撰寫的 WebAuthn 依賴方（RP），包含：

- 密碼 + RFC 6238 TOTP（6 位數、30 秒、±1 步視窗）；
- WebAuthn 註冊與登入（synced passkey 與 hardware FIDO2 key）；
- 一次性復原碼（10 組、每組 40 bits、scrypt 雜湊）；
- Email 重設權杖（32 bytes、SHA-256 儲存、15 分鐘有效、單次使用）；
- 伺服器端 session、撤銷、TOTP 輪替、速率限制與稽核紀錄；
- 一個故意惡意的反向代理（`evil.app.lvh.me:5011`），可即時轉送密碼、
  TOTP 與 WebAuthn assertion。

實驗使用 Chrome DevTools Protocol（CDP）虛擬認證器，透過 Playwright 驅動
真實的 WebAuthn 儀式。共執行 25 個控制情境（每個 3–5 次）、主要登入儀式
各 10 次延遲量測（復原流程 3 次），以及協定屬性檢查。所有資料來自實際執行，
沒有捏造的人類受試者資料；人類研究則以可執行的協議與問卷形式提供。

## 主要發現

### 1. 密碼 + TOTP 無法抵抗即時釣魚

攻擊者代理同時轉送密碼與當前 TOTP，**5/5 次成功登入**（平均伺服器/代理
時間約 47 ms）。攻擊者用過該組碼後，再從新的 session 重放，**5/5 次被
伺服器端計數器阻擋**；過期碼（±2 步）**3/3 次被拒**。這說明：

> 重放保護只能阻止「第二次使用」，不能阻止「第一次即時轉送」。

若伺服器沒有保存 `totp_last_step`，同一個碼可以被使用兩次（**5/5**），
證明重放防護必須是伺服器端狀態，而不是 TOTP 演算法本身。

### 2. Passkey 與硬體金鑰的釣魚抵抗，取決於 RP 是否檢查 origin

| 情境 | 方法 | 結果 |
| --- | --- | --- |
| 攻擊者使用自己的 RP ID（naive lookalike） | Synced passkey | 0/3 成功 |
| 攻擊者使用自己的 RP ID（naive lookalike） | Hardware key | 0/3 成功 |
| 轉送真實 challenge，RP 嚴格檢查 origin | Synced passkey | 0/5 成功 |
| 轉送真實 challenge，RP 嚴格檢查 origin | Hardware key | 0/5 成功 |
| 轉送真實 challenge，RP 錯誤信任 clientDataJSON.origin | Synced passkey | **5/5 成功** |
| 轉送真實 challenge，RP 錯誤信任 clientDataJSON.origin | Hardware key | **5/5 成功** |

這不是密碼學被破解。攻擊者位於 `evil.app.lvh.me`，而 RP ID
`app.lvh.me` 是它的後綴，所以瀏覽器允許使用該 RP ID；authenticator 也
確實簽了章。但 `clientDataJSON.origin` 是 `evil.app.lvh.me`，嚴格的 RP
會拒絕，寬鬆的 RP 則會接受。**同一把金鑰、同一個簽章，只因為驗證邏輯
不同，安全性就完全不同。**

### 3. 重放與簽章計數器

- TOTP 視窗：−1/0/+1 接受，±2 拒絕（各 5/5）。
- 捕獲的 WebAuthn assertion：同一個 flow 重放與新 flow 重放都
  **3/3 被拒**（flow 單次使用 + challenge 新鮮度）。
- 硬體金鑰「落後」的克隆：**3/3 被拒**（counter regression）。
- 硬體金鑰「超前」的偽造計數器：**3/3 被接受**。計數器只能偵測
  落後，不能偵測超前。
- 同步通行金鑰的非單調/零計數器：**3/3 被接受**，這是跨裝置同步的
  相容性代價。

### 4. 裝置遺失、備份與復原

- 同步通行金鑰在裝置遺失後可還原：**5/5 成功**。
- 沒有同步的平台憑證遺失：**3/3 鎖死**。
- 唯一硬體金鑰遺失：**3/3 鎖死**。
- 預先註冊的備用硬體金鑰：**3/3 可登入**。
- 硬體金鑰遺失後使用復原碼：**3/3 可登入**。
- 復原碼重複使用：**3/3 被拒**。
- Email 重設：第一次 200、重放 400、舊 session 被撤銷、舊密碼失效、
  新密碼 + 輪替後 TOTP 可登入，**3/3 全部成立**。
- 過期重設權杖：**3/3 被拒（400）**。

### 5. 可用性

量測到的登入儀式（不含人類思考與輸入）：

| 任務 | 中位數 |
| --- | ---: |
| 密碼 + TOTP 登入 | 158 ms |
| Passkey 登入 | 103 ms |
| 硬體金鑰登入 | 100 ms |
| 復原碼登入 | 94 ms |
| Email 重設送出 | 42 ms |

以 KLM（Keystroke-Level Model）分析模型估算的人類任務時間：

| 任務 | 估計 |
| --- | ---: |
| 密碼 + TOTP | 13.5 s |
| Synced passkey | 3.5 s |
| 硬體金鑰 | 4.0 s |
| 復原碼 | 9.2 s |
| Email 重設 | 18.2 s（不含郵件遞送） |

也就是說，passkey 與硬體金鑰在日常登入上約有 3–4 倍的人力時間優勢；
但硬體金鑰一旦遺失且沒有備份，成本不是幾秒，而是客服、身分驗證或永久
鎖死。**復原成本才是硬體金鑰部署的關鍵。**

## 建議

1. **以 passkey 作為消費者帳號的預設**，但 RP 必須嚴格比對
   `clientDataJSON.origin`、`rpIdHash`、challenge 與 UV。不要只驗簽章。
2. **不要把 TOTP 稱為釣魚-resistant**。它可以作為第二因素，但即時轉送
   仍然有效；請保留伺服器端重放計數器、速率限制，並對敏感操作要求
   更強的因素。
3. **硬體金鑰部署必須同時註冊備用金鑰**，並提供一次性復原碼。沒有備份
   的硬體金鑰是營運風險。
4. **復原流程要用與登入相同的威脅模型設計**：單次使用、短效、原子消耗、
   session 撤銷、TOTP/密碼輪替、速率限制、避免帳號列舉。
5. **同步通行金鑰要提供帳號層級的憑證撤銷**。刪除裝置或 App 不一定能
   撤銷已同步的憑證；伺服器端撤銷才是可靠來源。
6. **測試負面情境**：錯誤 origin、錯誤 RP ID、重放 challenge、過期
   token、重複使用復原碼。只測 happy path 會高估安全性。

## 限制

- 使用 Chrome CDP 虛擬認證器，並非實體金鑰；不模擬廠商雲端同步的內部
  實作。
- 所有伺服器在 loopback，沒有 WAN 延遲與真實郵件遞送。
- 每個情境 3–5 次，Wilson 信賴區間很寬；結果是協定層級的定性結論，
  不是母體比例估計。
- 僅使用 Chrome；未測試 Firefox/Safari 的差異。
- 沒有人類受試者資料；可用性部分是 KLM 分析模型與質性比較。
- 未進行形式化驗證（例如 ProVerif/Tamarin）。

## 結論

Passkey 與硬體金鑰確實比密碼 + TOTP 更能抵抗釣魚，但這個優勢不是自動
成立的：它取決於 RP 是否正確驗證 origin，以及復原流程是否同樣堅固。
TOTP 的重放保護很重要，但它只處理「第二次使用」，不處理「第一次即時
轉送」。同步通行金鑰用「可用性」換來「較弱的克隆偵測」，硬體金鑰則用
「非可匯出性」換來「遺失即鎖死的風險」。最終，帳號安全是一個系統性質：
憑證、驗證邏輯、復原流程與營運政策必須一起設計。
